INTRODUCTION TO HCI REFERENCE
WHAT IS HCI?
The Host Computer Interface (HCI) is an interface which can be used to connect
a Clear-Com matrix communication system to another system (the "host"). This
can enable an integration into a larger system where certain, or all, operations
of the are remotely controlled, preset, or automated using third party software
or controllers.
Most types of Clear-Com matrix can be configured and controlled remotely.
EHX it is a person-machine interface for configuring the operation of the ClearCom matrix. EHX uses the HCI API for real-time control of the matrix. This HCI
API is available for third-party client development.
When using HCI, it is necessary to set up a baseline "map" configuration in EHX
and download it to the matrix in the same way as if the Clear-Com system were
operating as standalone.

WHO USES HCI?
HCI is a standard to which you can work. It is platform independent; you write
your own routines in your normal operating system to enable the host to talk to
the Clear-Com matrix.
HCI requires a competent programmer to implement.
This document is intended to be used by customers who wish to control the
Clear-Com Central Switching Unit (CSU) using the Host Computer Interface
(HCI).

WHAT HCI COMPRISES
HCI is ordered as an option for Clear-Com matrix systems. It comprises of:

TYPE OF MESSAGE
Messages to the matrix from the host are of two types:
• Action Request. This is a request to the matrix to do something.
• Status Request. This is a request to the matrix to provide some
information.

distinction between them is different):
• Solicited Message. This is sent in response to a status request.
• Unsolicited Message. This is a message from the CSU reporting a change
in the system operation or status which the host did not request.

OVERVIEW
START UP
When the CSU is powered up or reset, various aspects of the CSU are reinitialised including the communications hardware and software.
During reset process, spurious characters may be sent to the host by the CSU
on a data connection. A correctly implemented protocol will ignore these
characters. Should the host send a message whilst the CSU is resetting, no
acknowledgement (ACK) of the message will be given by the CSU.
When the reset sequence has been completed by the CSU, the protocol will
attempt to establish the communications link. If valid packets are transferred
without error, the CSU will then send an automatically generated Reply CPU
Status message. This message tells the host that the CSU is now in the running
state and is ready to receive and process further commands.

THE RUNNING STATE
Once the CSU has sent the first Reply CPU Status message, the host can then
send and receive messages to and from the CSU as required. During normal
operation, the host can request the CSU to carry out an action and the CSU
generates replies to keep the host informed of what changes take place. Not all
of the messages that may be generated by the CSU are documented here, and
any unspecified messages that are received by the host should be ignored.

REPLIES AND REQUESTS
Messages between the host and the CSU are of two types, request or reply. The
host "requests" that the CSU takes some action and the CSU "replies" with
information about one particular feature of the CSU.
There are two sorts of request available to the host. The CSU can be requested
to carry out an action or to report some status information. For instance, the
Request Conference Actions message is used to connect or disconnect a port to
or from a conference and a Request Conference Status message causes the
CSU to generate a reply telling the host about the ports currently connected to
the specified conference.
Reply messages may be generated by the CSU in response to a request by the
host or when the status of some part of the system changes. The messages
generated in response to a request contain a snapshot of the feature that has
been requested. An automatically generated reply message typically contains
only the information of the feature that has changed.

Page 52

BROADCAST SYSTEM MESSAGES
When the host sends the first "System Request Messages" to the CSU, the CSU
will send all Broadcast System Messages that may have been queued since CSU
reset. There is a limit to the size of the queue of 600 messages. These
messages convey textual information about the status of the system, many of
which may be ignored during normal operation. Two fields are provided to allow
the easy filtering of these messages, so that only desired messages need to be
fully processed.

SYSTEM FEATURES
There are two types of status message available to report on the current
operating status of the system, CPU Status and System Status messages.
The Request and Reply CPU Status messages should be used to find out what
state the processor is currently in, what type of reset was last executed by the
processor and how long the processor has been the master processor. The host
computer should track any CSU resets using the Reply CPU Status message as
certain types of reset may clear out assignments that have been made by the
host.
The Request and Reply System Status messages should be used to find out the
current status of each board in the system.
The only action type message for the CPU is the Request CPU Reset message.
This message should be used to execute one of two types of system reset that
are available. Once a Request CSU Reset message has been sent by the host,
the CSU will ACK the request and then execute the requested reset.

CROSSPOINTS
The host computer may request an action on any crosspoint within the CSU.
This message should be used to create or remove a uni-directional audio route
between two specified ports. There are four possible actions that can be
achieved using this message:
• To actively enable it (add enable)
• To cancel the enable (delete enable)
or
• To actively inhibit (block crosspoint) it (add inhibit)
• To cancel the inhibit (delete inhibit)
For a remote system only the first two are available; the inhibit facility cannot
be used.
An add enable request will attempt to create the specified audio path through
the crosspoint and a delete enable will attempt to remove the specified audio
path. An add inhibit request will attempt to actively cause a disconnection of
Page 53

block the audio path through the crosspoint, and a delete inhibit request will
cancel this attempt. The outcome of an add enable request and add inhibit
request clash on a crosspoint depends on the priority associated with each
request, but if they are of the same priority, the inhibit will succeed.
Each add enable action for a crosspoint is stored on an action stack. If two add
enable actions are received by the CSU (from whatever source) for a
crosspoint, then two corresponding delete enable actions are required to cancel
the enable actions; one for each enable action stored on the stack. The delete
enable actions remove exactly equivalent add actions from the action stack and
are not stored. In general, the host should avoid using more than one
simultaneous request to turn on or inhibit a crosspoint.
In order to monitor the changes to a specified range of crosspoints, the
Request and Reply Crosspoint Status messages should be used. The CSU also
generates Reply Crosspoint Status messages whenever a crosspoint changes
state, and a full regular update once a minute.

CONFERENCES
Conferences (partylines) in the CSU are implemented by mixing the input
signals of all talkers on the conference and feeding the result to all listeners on
the conference. Any talkers that are also listening to the conference will not
hear the result to prevent feedback. This mode of operation is also known as
"mix-minus". It is also possible to connect other audio sources to a given
conference using request conference actions from the host or Clear-Com
panels.
The Request Conference Actions message allows the host computer to connect
any given port to any given conference as either a talker or a listener. To
connect a port as a talker and a listener, two actions must be sent, one to
connect the port as talker and another to connect the port as a listener. One
port may be connected to multiple conferences by sending multiple conference
actions. Disconnections of ports from conferences are achieved by sending
delete type actions. The message format also supports the sending of multiple
conference actions in one Request Conference Actions message.
Conference actions are very similar to crosspoint actions in that they have the
same direction bit mechanism to connect and disconnect a port. However,
there is no inhibit mechanism. Conference actions also operate on the
individual crosspoint stacks in the same way as crosspoint actions.
The Request and Reply Conference Status messages should be used to
determine the current state of any of the conferences in the CSU. The CSU will
automatically generate Reply Conference Status messages whenever any
change to the conference status is detected.

Page 54

GENERAL PURPOSE INPUTS AND OUTPUTS
General Purpose Outputs (GPOs) are used to control equipment that is external
to the CSU with each output having two possible states, on or off. When on, a
circuit is made via relay contacts and when off, the circuit is broken. The
normal state is off (open circuit).
General Purpose Inputs (GPIs) are used to stimulate actions within the CSU.
When a GPI is pulled down to 0V, the input is on and any control programmed
via EHX is executed. The normal state of the input is high.
A special function output (SFO) simulates a GPI being connected directly to a
GPO but the SFOs have no physical inputs or outputs. SFOs are equivalent to
Controls in EHX.
The Request GPO/SFO Actions message should be used to control the state of
specified GPOs or SFOs. GPO/SFO actions have an equivalent to the crosspoint
stacks and have an identical inhibit/enable mechanism for adding and deleting
GPO/SFO actions.
The state of the matrix GPIOs and SFOs can be monitored on a per card basis
using the Request and Reply GPIO/SFO Status messages. Each card can be
either be a GPIO card or a SFO card. The type of card, GPIO or SFO, is
determined by the configuration of the CSU.

AUDIO LEVEL CONTROL
There are different methods of controlling the audio levels in the Clear-Com
matrix. These control the input, output and crosspoint levels, and can alter
these levels as described below.
The level of the signal entering the matrix may be controlled using the Request
Input Level Actions message. The current settings of the input levels can be
determined using the Request and Reply Input Level Status messages. Input
level controls act independently of any crosspoint and output level controls.
Output level control is provided in a similar manner to input levels and for all
outputs is altered by digital processing. The messages used are Request Output
Level Actions, Request Output Level Status & Reply Output Level Status.
Crosspoint level control is provided by digital processing. The messages used
are Request Crosspoint Level Actions, Request Crosspoint Level Status & Reply
Crosspoint Level Status.
Input and output level control will conflict with an Assignment Panel controlling
input and output levels. None of the level controls outlined above will conflict
with panels controlling crosspoints routed to themselves.
The resultant level of a crosspoint is the combination of input level, crosspoint
level and output level - for example if the input level is -3dB, the crosspoint
level is +4dB and the output level is +5dB, then the actual gain from input to
output is +6dB.
Page 55

KEY ASSIGNMENT
The assignment of keys on Clear-Com panels can be achieved by using the
Request Locally key Actions message. A list of the key assignments that have
been made by the host computer can be accessed using the Request and Reply
Local Key Action Status messages.

CONFIGURATION FILES
It is possible to interrogate the CSU to find out information about the
configuration of the CSU. The configuration map information must have
previously been sent to the CSU using configuration files or be present in the
Flash memory fitted to the CPU card. By using the Request Configuration File
message the map signature table can be requested. The CSU returns this with
the Reply Configuration File message. The .SIG file is sent automatically by the
CSU, so that the host can be informed immediately if the map changes at any
time. This may occur when the CSU is reset or a new map has been
downloaded using EHX.

ACTION STATUS
The Request and Reply Action Status messages are used to keep the host
informed of the current actions that have taken place in the CSU. Whenever a
Request Conference, Crosspoint or GPIO/SFO Action message is processed by
the CSU, the CSU will respond with a Reply Action Status message that echoes
the action(s) contained in the Request. Should the host lose track of the actions
that it has requested, the host should send a Request Action Status message.
The CSU will then generate a list of all the actions made by the host and send
them in as many Reply Action Status messages as needed.

SENDING MULTIPLE COMMANDS
The user must check that a reply message has been received when sending
commands to the CSU. For example, after a "Request Crosspoint Actions"
message, the CSU will confirm receipt of the message by issuing a "Reply
Actions" message. If this message is not received, the request was lost.

TRANSPORT PROTOCOLS
ETHERNET LINK
The Ethernet Link uses TCP/IP to provide a secure data stream. In order to
maintain a packet orientated interface, each data packet is formatted as shown
below, and must be transmitted with a TCP/IP "Push" command to ensure the
complete data packet is transmitted at the appropriate time.

3.1.1

Packets Structure
All transport packets have the same structure which is:

The start and end fields, 16 bit words, allow synchronisation of data in the TCP
stream.
The length field, 16 bit word, holds the number of bytes of the complete
transport packet.
The message field may contain between 2 and 836 bytes of data. The contents of
this field are described in the message description section.

3.1.2

Connection Ports
After CSU reset the active connections are reset and a range of ports will be
passively opened. It is up to the user to regulate which hosts attach to which
ports. All ports are treated equally by the CSU.
Available ports: 52001 - 52020
Any Host IP address and port number is accepted as a connection. Only one
Host can connect to each of the available ports at a time.

3.1.3

Ping Facility
An HCI ping facility has been provided to allow the Host to periodically check
that the CSU is alive. If the CSU receives a packet with a size of 10 message,
thus:
5A 0F 00 10 00 00 2E 8D
It will be echoed back to the relevant Host.
Excluding network delays, the CSU should respond in less than one second.
Since TCP/IP is a secure protocol no retries are required - if the echo is not
Page 57

received within a few seconds (allowing for other data on the link and the
network delay) then the CSU is not alive.
.

3.1.4

Client Session Closure
When ending the HCI session with the matrix central equipment the HCI client
should forcefully close the socket connection, as opposed to gracefully flushing
the socket before closure.
This approach results the RST bit being used to close the socket as opposed to
the FIN bit that signals the need to flush.
The nature of the traffic on the HCI TCP socket makes the reliability of the FIN
based closure uncertain and less reliable.

INTRODUCTION
This section describes the message field of the transport packet. It is made up
of a number of fields, the message ID, the flags field, the protocol identification
fields and the message data field. The message ID field identifies the type of
message and is the first 16 bit short of the message field. The third byte is the
flags field and is described in detail below.
The protocol identification field is used to differentiate HCI 1.0 and 2.0
messaging and to provide future backwards compatibility.
The remaining bytes of the message field form the data section of the message
which has a maximum size of 834 bytes. The contents of this field are
described in detail in the message description section.

FLAGS
The flags field is used by the host and the CSU to allow the recipient of the
message to deal with it correctly. The exact usage of the bits in this field are
explained below.

Protocol identification
Every HCI 2.0 message contains a protocol identifier and protocol version
number (schema). The four bytes following the flag byte will always be 0xAB,
0xBA, 0xCE, 0xDE. The presence of these bytes indicates that this is an HCI 2.0
message.
This is followed by the protocol version byte. The initial version of every HCI 2.0
message is 0x01. If the payload of a message changes in subsequent versions,
the version identifier will be incremented to allow reference to the appropriate
message structure.

FIELD SIZE LIMITATIONS
The message structure has been designed to allow for expansion up to a
maximum of 1024 ports but the actual limits depend on the size of the system.
The ranges given in the messages section are the maximums allowable by the
protocol and not for the system that has been supplied.
Note: The Host Computer Interface has been designed to process correctly formatted
messages efficiently. Messages that are sent by the host that are out of range
may not be correctly processed by the CSU. It is the responsibility of the host
computer to ensure that values sent to the CSU are within the range of the
equipment currently installed in the CSU. No messages are provided to inform
the host that the message was not understood by the CSU.

Set Panel Audio Front End State Request
4.111.1

Description
This message is used to set the HCI requested state of the panel MIC,
speaker and sidetone state.
When enabled, the state of the panel is exactly as though a talk key has
been pressed. This HCI request simply acts as though a virtual talk key is
pressed.
For example, if a panel talk key is already pressed and the HCI request is
received then the panel audio hardware state does not change. However, if
the panel talk key were now released the panel mic, sidetone etc would
stay in the same state i.e. as though a talk key is still pressed, until the
HCI disable equivalent of this message is received by the matrix.
This message is useful when e.g. a 3rd party application is using the HX

GLOSSARY
Analog Port
Any of the Eclipse matrix’s analog input/output RJ-45 connectors that are used
to connect cable from the matrix to panels and interfaces. Each “port”
connects to a separate audio channel in the matrix intercom system.
Bus
A bus is the channel or path between the components in the matrix along
which electrical signals flow to carry information from one component to the
next.
Call Signal
A call signal is an electronic signal sent from one panel or interface to another.
A call signal can be audible and/or visual.
Typically a call signal is sent to get the attention of a panel operator who may
have turned down their intercom speaker’s volume or removed their headset.
It can also be sent to activate an electronic relay.
Category-5 cable
EIA/TIA 568 category specification relating to network cabling. Shielded
category-5 cabling is required for Eclipse matrix wiring.
CellCom
Digital wireless communications product. Sold under the CellCom name in USA
and as FreeSpeak in Europe and Asia.
Central Matrix
The term “central matrix” is used to differentiate the central hardware and
software of the intercom system from the connected audio devices. The central
matrix consists of:
• The metal housing for the circuit cards and power supplies.
• The circuit cards.
• The power supplies.
• The rear panel connectors which connect the matrix’s hardware to panels
and interfaces.
Destination
A device such as an intercom panel, beltpack, or interface to which audio
signals are sent. The device from which audio signals are sent is called a
“source”.
Duplex
All real-time communication between individuals talking face to face is full
duplex, meaning that they can both talk and listen simultaneously. The Eclipse
matrices provide full-duplex audio.
EHX
Eclipse HX Configuration System. Software program that guides the operation
of the central matrix circuit cards and connected panels.
Page 366

Ethernet
International standard which describes how information is transmitted across a
network. Provides for the efficient organization of network components.
Fiber-optic Cable
A fiber-optic cable consists of a glass core covered with a reflective material
called “cladding” and several layers of buffer coating to protect the cable from
the environment. A laser sends light pulses through the glass core to the other
end of the cable.
FreeSpeak
Digital wireless communications product. Sold under the FreeSpeak name in
Europe and Asia and CellCom in USA.
FreeSpeak II
Enhanced Digital wireless communications product.
Full Duplex
Refers to transmission of signals in two directions simultaneously.
IFB
Interruptible Foldback. The term “foldback” refers to sending “program” audio,
or some other audio mix, back to announcers while they are on the air. Doing
so allows announcers to monitor themselves, other announcers, videotapes of
commercials, or some mix of sources, while they on the air. This is typically
found in television news and live broadcast events.
Announcers typically wear a small ear piece so they can hear the selected
foldback audio mix. When a director wants to give directions to an announcer
on air, or to announce changes in the program, the director must “interrupt”
the foldback. To do this, the director uses a channel specifically set up to
interrupt the foldback audio.
Interface Module
A piece of electronic hardware designed to convert the 4-wire signals of a
central matrix port to some other form of communication, such as 2-wire party
line, telephone, etc. The interface module is connected to a central matrix
port. The external non-4-wire device is then connected to the interface
module.
ISO
The ISO function, short for “panel ISOlation”, allows a panel operator to call a
destination and interrupt all of that destination’s other audio paths and
establish a private conversation. When the call is completed the destination’s
audio pathways are restored to their original state before the interruption.
IV-R
Instant Voice Router. Software that routes digital audio data between Concert
users and between Concert users and Eclipse systems.
Label
A label is an alphanumeric name of up to five characters that identifies a
source, destination, or control function accessed by an intercom panel. Labels

appear in the displays of the intercom panel. Labels can identify panels, ports
interfaced to other external equipment, fixed groups, party lines, and special
control functions.
Mode
A term used to describe a light path through a fiber as in multimode or single
mode.
Multimode Fiber-optic Cable
The glass core of a multimode fiber is larger than the core of a single mode
fiber, which causes the transmitted light beam to disperse as it travels through
the core. Single mode fiber, with its smaller core, concentrates the light beam
so that it carries signals further. Multimode fiber was the first type of fiber
offered by manufacturers. Single-mode fiber evolved as production methods
improved.
Multiplexing
The process by which two or more signals are transmitted over a single
communications channel. Examples include time division and wavelength
division multiplexing.
Nanometer (nm)
Common unit of measure for wavelength. One billionth of a meter.
Non-volatile Memory
Data stored in the CPU’s firmware (ROM) that is not lost when the power is
turned off.
Optical Signal
A laser at one end of a fiber-optic cable pulses on or off to send a light signal
through the glass core of the cable to the other end of the cable. Because the
light signals are binary (on or off), the signal is digital.
Panel
Also referred to as “station” in some cases (usually older manuals). Any
intelligent intercom device connected to the rear-panel analog ports of the
central matrix. This term does not refer to devices connected through interface
modules.
Port
Any of the input/output connections (RJ-45 connectors) on the back panel of
the central matrix. These connectors and the attached cables connect the
central matrix to remote intercom devices. The term “port” emphasizes that
the connection is a “portal” between the central matrix and the remote
intercom devices.
Program
Any separate audio source that is fed into the intercom channels. In television
applications, for example, “program” audio is the audio that is broadcast on
air.

Rack Unit or RU
Standardized unit of mounting space on a rack panel. Each rack unit is 1.75
inches (44.45 mm) of vertical mounting space. Therefore 1 RU is 1.75 inches
(44.45 mm) of vertical mounting space, 2 RU is 3.5 inches (88.9 mm), 3 RU is
5.25 inches (133.35 mm), and so on.
Remote Panel
Any intelligent intercom device connected to the back-panel ports of the
central matrix. This term does not refer to devices connected through
interfaces.
Sidetone
The sound of the panel operator’s own voice heard in their own earphone as
they speak.
Single-mode Fiber-optic Cable
The glass core of a single-mode fiber is smaller in diameter than the core of a
multimode fiber, so that the light signal transmitted over the core is more
concentrated than with multimode fiber, which allows the signal to travel
further. Single-mode fiber evolved from multimode fiber as production
methods improved.
Source
In this manual, the term “source” refers to a device—such as an intercom
panel, interface, or beltpack —that sends audio into the matrix. The device to
which audio is sent is called a “destination”.
VOX
In the Eclipse system, when audio at a panel exceeds a threshold, a light
switches on at the panel’s port card to visually cue the operator. The threshold
level is set in the Eclipse Configuration Software.
V-Series
Communications panels used with Eclipse systems providing advanced
facilities. Available in rack mount and desktop formats.
Wavelength-division Multiplexing (WDM)
A method of multiplexing optical signals developed for use on fiber-optic cable.
Each signal is assigned a particular wavelength on the light spectrum and
therefore many signals can be transmitted simultaneously without interfering
with each other.
